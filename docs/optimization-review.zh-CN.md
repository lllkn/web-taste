# Web Taste 优化评估

评估日期：2026-10-05。基于 `main` 分支提交 `607e0b6`，仓库来源：https://github.com/lllkn/web-taste。

本文保留修复前的评估结论与验证范围；当前已完成的修复见[修复与验证记录](fix-verification.zh-CN.md)和[更新记录](../CHANGELOG.md)。文中的代码行号对应上述历史提交。

本次完成本地克隆、全部指令与脚本阅读、现有回归测试和临时数据复现。没有修改 skill 的行为或脚本。下文区分已复现问题、指令冲突和基于源码的风险判断。

## 判断

应保留“从参考站提炼关系 → 展示证据 → 确认偏好 → 按新任务筛选应用”的核心。优势是区分观察与解释、保留来源和适用边界，并验证真实响应式效果。

下一版最有价值的工作是让记忆可持久保存、审批语义一致、记录可可靠校验、证据真正可视比较。继续增加通用审美规则的收益较低。

## 优先级与证据

| 优先级 | 问题 | 依据 | 建议 |
| --- | --- | --- | --- |
| P0 | 私人记忆混在 skill 安装目录，摘要与索引仍被 Git 跟踪 | `taste_library.py:12` 将运行数据根固定为 skill 的 `references/`；`git ls-files` 包含 `taste-profile.md` 与 `site-index.md`；`.gitignore` 仅忽略三个内容目录 | 分离发布资源与运行数据，增加 `--library-root`；旧库备份后迁移 |
| P0 | 多个网站的共同特征可被提升为用户偏好，和“只记住用户批准内容”冲突 | `SKILL.md:21` 要求审阅；`:67` 又允许显式认可 **或** 多个来源支持；profile 模板重复此规则 | 来源数量只影响观察可信度；用户偏好必须有明确认可及范围 |

| P1 | 网站级确认不足以表达部分认可与后续撤回 | 当前只有网站 `review_status` 和自由文本 review | 给可复用原则设置稳定 ID，记录逐条认可、条件、否定和替代关系 |
| P2 | 确认流程偏重，Learn-and-apply 容易多次暂停 | “完成每个 gate”与“只有实质选择未决才暂停”并存 | 区分工作范围、长期记忆授权、关键设计选择；合并可同时解决的选择 |
| P2 | 命令路径依赖调用时工作目录 | `python3 scripts/...` 在目标项目根运行会找不到脚本 | 明确相对于 skill 根解析脚本，数据根单独指定 |

| P2 | 组件方案共享报告文档的 CSS 与脚本环境 | `preview_html` 直接注入同一文档 | 优先实际组件截图；需要 HTML 时用独立 iframe 隔离样式，并明确视口 |

P0 表示影响核心记忆语义或数据生命周期；P1 表示影响可信性与复用效果；P2 表示使用体验与兼容性。

## 1. 先分离 skill 与个人记忆

现在 `references/` 同时承担静态说明和可变用户数据库。用户修改 profile 后，如果提交整个仓库，摘要可能被带入公开提交；索引会包含源站标题、URL 对应的记录名等信息。升级安装是否覆盖旧数据取决于安装器，当前仓库没有独立数据根和迁移机制，因此存在升级风险，并非本次观察到实际数据丢失。

建议结构：

```text
web-taste/                       # 可升级的发布内容
  SKILL.md
  references/                   # 分析规范与格式说明
  scripts/

<用户选择的 library-root>/      # 持续保存的个人数据
  profile.md
  index.md
  sites/
  reports/
  applications/
  decisions.jsonl
```

数据位置可用 `--library-root` 显式指定，并提供用户数据目录的默认值。无需一开始使用数据库。迁移要保留原库备份、相对报告链接和迁移版本；再次执行不能重复生成偏好。临时补丁仅增加 ignore 不够，因为已经被 Git 跟踪的文件仍会被提交。

## 2. 把“观察可信度”与“用户认可”分开

多个参考站都使用大标题，说明这是一种常见设计方式，不能证明用户喜欢大标题。即使用户批准一份分析报告，也不一定认可里面每个特征适用于未来项目。

建议统一规则为：

> 只有用户明确认可的原则可以进入偏好层。多个独立来源可提高该原则的观察可信度，但不能代替用户认可。区分本次项目选择与长期偏好；记录认可的适用范围。

每个原则只需增加最小可追溯信息：`id`、`evidence_refs`、`observation_confidence`、`user_decision`、`scope`、`use_when`、`avoid_when`。用户说“只喜欢导航，其他不保留”时，应能批准导航原则，排除其余原则，而不是只设置全站 `confirmed`。

后续“以后别再用这个”应能撤回或替代已有偏好。`profile.md` 可以是便于阅读的摘要，原始认可记录保留在决策日志中。不要把一次组件选型自动扩大成所有项目的偏好。

## 3. 修复已复现的脚本问题

所有复现数据都放在临时目录，不污染个人库。

| 实验 | 实际结果 | 应有行为 |
| --- | --- | --- |
| 完整 reviewed record 的正文加入 `[Screenshot](report.html)` | 被判为占位符 | 接受正常 Markdown 证据链接 |
| reviewed record 设置 `source_url: ""`、`captured_at: "not-a-date"` | 校验通过 | 拒绝空 URL 和非法日期 |
| frontmatter 使用合法的 `review_status: 'confirmed'` | 解析结果保留单引号 | 得到字符串 `confirmed` |
| 对“古诗展示页”和“个人档案”运行 `slugify()` | 都得到 `record` | 生成不同的记录 ID |
| 无截图、无 evidence 条目、无 gaps 说明的 board | 成功生成 HTML | 明确为证据不足草稿，并要求缺证说明 |
| Display 和 Caption 使用不同 `spec` | 生成的行没有各自字号样式 | 若称为字号阶梯，应展示字号关系，缺字体时说明替代字体 |

占位符误判源于 `taste_library.py:320` 的通用方括号正则。建议用专用 `TODO:` 标记或明确的 scaffold token；不要把所有方括号内容都当未完成字段。

frontmatter 当前是手写行解析，不支持常见 YAML 写法。可以选择显式依赖 YAML 解析器；若要继续只用标准库，可以让机器数据采用 JSON，并生成 Markdown 阅读版。无论选哪种，都应明确格式约束并验证 URL、日期、枚举和必填值。

对 board 不必一律强制截图：访问受阻时仍可提供部分报告，但应有 `draft/incomplete/reviewable` 状态，缺证原因可见，证据不足的原则不能被标成充分验证。

## 4. 让 Board 直接支持设计判断

当前色板已经具备视觉表达，字号、间距主要还是数值卡片。建议第一步增加：

- 字号样本按采集到的 size、weight、line-height 展示；无法加载实际字体时明确标注替代字体。
- 间距与容器关系用比例图展示，布局骨架对应真实章节与对齐线。
- 桌面与移动截图保留视口标签；原则通过 evidence ID 指向对应截图、区域或状态。
- 只在 scope 包含交互或动效时展示状态组、关键帧与时间信息；不强制每个任务补齐全站维度。

`preview_html` 与报告位于同一文档，方案内的通用选择器可影响其他方案，报告本身的 `h1`、`body` 等规则也可能影响样本。这是源码可见的隔离风险，本次没有做浏览器视觉复现。使用实际组件截图或隔离 iframe 后，应验证各方案在相同视口和内容下可比较。

组件选择按钮现在只改变页面显示，并提示用户在对话中报告选项。没有把选择自动写回决策库。可以明确保持这种手动反馈方式，或提供可复制的决策摘要；不要将点击显示状态当成已持久化的审批。

## 5. 改进检索与冷启动

先做轻量 `search`，无需立即增加向量数据库。索引增加信息密度、内容形态、交互模型和情绪方向等少量维度。候选筛选以认可状态、任务适配和排除条件为先，再选择最相关的来源。

区分“来源观察记录可供参考”与“已认可偏好可指导应用”。`corrected` 记录也可能包含被拒绝原则，不能全盘导入。拒绝方向可用于避免重犯，但不能作为正向融合来源。

明确这些分支：

- 库为空：根据本次 brief 工作，说明没有历史偏好支撑。
- 只有一个相关来源：使用一个，不补凑 2–4 个。
- 没有匹配来源：先依照目标内容、功能和既有设计系统；新参考学习可按需触发。
- 有冲突：按用户本次明确要求、已认可的适用范围和可用性解决；必要时展示一个具体选择。

## 6. 收敛指令，减少不必要确认

已有“原请求清楚即可视为确认”的规则值得保留，但需要贯穿 Learn、Apply 和组合模式。建议统一为：范围和交付已明确时直接执行；缺少会影响结果的重要选择时再询问。把需要用户审阅的长期记忆变更集中呈现。

例如“分析这个网站，只看字体，不存库”应直接完成字体分析；“参考这个站重做当前页，你自己决定”应能形成可审阅实现，不因可逆设计选项反复暂停；“我认可 A 的导航但不喜欢其动效，保存下来”应精确保存导航认可与动效排除。

description 建议收窄为“从参考网页学习可迁移设计关系，审阅并保存用户认可偏好，或按已存偏好指导界面设计”。当前“多个组件方向需要选择”可以吸引普通组件工作，不一定需要学习或记忆系统。保留用户指定的框架、设计系统和已授权素材；`Never copy` 应围绕未经授权复制第三方身份与资产，避免阻碍用户自己的素材或合法可用资源。

## 推荐实施顺序

1. **可靠性修订**：分离数据根、统一偏好认可规则、修复校验和记录 ID、补充真实失败案例的回归测试。
2. **证据与检索修订**：真实字号与布局对照、原则级证据链接、状态过滤、冷启动与少量来源分支。
3. **体验修订**：合并确认、隔离组件预览、处理部分认可和撤回、明确脚本绝对路径与浏览器能力不足时的降级方式。

## 验收与本次验证范围

优先用可观察行为验收：升级后旧库保持完整；正常链接可保存；缺证草稿不能伪装为充分验证；用户部分认可只改变指定原则；撤回后不再作为正向偏好；空库和单来源任务都能完成；目标项目根目录可正确调用脚本。
